# Provider build modes

R1.5.1 keeps PUBLIC as the default. `cargo build --release` and `npm run tauri build -- --bundles nsis` require no maintainer credentials. Install locked dependencies and restore the fixed mpv runtime using the existing instructions first. PUBLIC Release starts unconfigured, ignores development/legacy release credential variables, and retains the native JSON picker for a user's legally held credentials for this process only. Video playback and local XML/ASS remain available.

OFFICIAL is selected only by process environment `MIRY_PROVIDER_BUILD_MODE=OFFICIAL`. A trusted local supervisor must provision these non-secret paths before launching the same build command:

| Variable                        | Contract                                                                                                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `MIRY_PROVIDER_BUILD_ROOT`      | Dedicated absolute temporary directory outside source/Git; owner-only ACL, no cloud sync, backup or remote cache upload.                                           |
| `CARGO_TARGET_DIR`              | Absolute directory inside that root. All generated modules, objects, PDBs, EXEs and installers stay here.                                                          |
| `MIRY_PROVIDER_CREDENTIAL_FILE` | Fresh file inside that root with only JSON string fields `appId` and `appSecret`. Values must never be command arguments, Cargo variables, rustflags or rustc-env. |

The supervisor obtains credentials through masked local input or an audited private secret manager. Never send them through chat. App ID accepts 1–128 ASCII letters, digits, dots, underscores or hyphens. Secret accepts 8–512 printable ASCII characters without whitespace. JSON is limited to 8 KiB; incomplete, malformed, inaccessible, oversized or unknown-field input fails. Unknown modes, source-local paths and output outside the isolated target fail. Errors withhold values. Generation and readback must succeed before OFFICIAL is enabled; it never falls back to an unconfigured official package.

Use a fresh unique credential filename/root per official build; do not preserve file mtimes or reuse cached official artifacts after credential changes. Cargo tracks the file and non-secret mode/path changes. Credentials are deliberately not environment inputs, preventing values entering Cargo's environment fingerprints. Generated byte arrays are reversible representation, provide no real client key secrecy, and binaries contain extractable credentials. Restrict the entire build root, including incremental caches and crash dumps. Only deliberately approved official release artifacts may leave it. Never commit those artifacts or upload them to a private review branch.

Build in a disposable allowlisted environment: separate USERPROFILE/HOME/AppData/ProgramData, TEMP/TMP, Cargo/npm homes and config; no inherited Provider variables, user tool config or production Miry Profile. Provision only reviewed compiler environment, dependency caches and fixed runtime. Do not launch a GUI/installer in a production identity for testing. The private synthetic verification runner demonstrates this isolation and accepts no real credentials. An unreviewed shared CI is not an approved injection channel.

OFFICIAL startup selects the native bundled identity before debug overrides. Status returns only configured/mock/builtIn booleans. Existing native configuration behavior protects the built-in identity and never writes user configuration or a Profile. Signature, paths, failures, throttling and cancellation retain their implementation. PUBLIC Debug retains explicit development inputs; PUBLIC Release ignores them.

Before actual distribution, confirm the application's approved service scope, tier/quota and terms in the official account. Synthetic builds establish neither authorization nor real service availability. Rotation requires a fresh protected input/root, rebuild and validation, followed by separate distribution/revocation authorization. Revoking keys can disable old clients' online access; video/local danmaku remain independent. No backend, proxy or update service is introduced.
